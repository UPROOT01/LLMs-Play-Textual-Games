Game: TextWorld cooking, levels 1, 3, 5, 7, 9, 100 steps at most. Score = share of the recipe's points; won = the meal prepared and eaten.

System

Benchmark on vLLM: many games at the same time

GridA YAML file lists models × modes × prompts × levels × seeds. Each game is saved as one JSON record with its log.
→
RunnerGames already played are skipped, so a run can be stopped and resumed on Colab or on the remote 4090.
→
EngineEach game runs in its own thread and sends its requests to one vLLM instance.

Inside vLLM

  • Continuous batching: a request joins the batch already being generated, so a game does not wait for the long reasonings of the others.
  • Prefix caching: the part of the context already read in the previous turns is not computed again.

Number of games in parallel: automatic

  • The limit is the KV cache: the memory where vLLM keeps the contexts of the requests it is generating.
  • The engine starts a new game only when there is room for it, and adjusts the limit while the run goes on (next slide).

Before: one game at a time with transformers, the GPU mostly idle. Times are now wall-clock times of games played together, so the modes are compared by tokens, not by seconds.

System

Parallel games: KV cache target adjusted to the pauses of vLLM

The problem

A full cache does not slow the generation. A pause does: when no memory is free, vLLM stops a request and computes its context again later.

First minute: estimate

A game counts for the memory its requests are expected to hold (75th percentile of the finished games of its mode). Games start while the estimates fit in 90% of the cache.

After one minute: measure

The real cache usage and the pauses are read from vLLM. A game starts if the usage plus the new game stays under the target: 92%.

The target follows the pauses

  • More than 5 pauses in a minute: −5 points (not below 60%).
  • A minute without pauses: +2 points (not above 92%).

The estimates were about 1.6 times the real usage: the GPU was used at about 60%. A pause only costs time, never changes a result.

Model families, checks and tools

One profile per model family

Qwen3, gpt-oss. A profile is the code that writes the conversation in the format that family was trained on, and that forces or forbids thinking. Checked against the format published by the model's authors.

The games played before vLLM, are imported as records and appear in the same tables as the new ones.

Finding 2 · holds in both families

When the model thinks does not matter

Summary

Supported

  • The amount of thinking has a low ceiling 2 families
  • The moment of thinking does not matter 2 families
  • Keeping the last reasoning doubles the wins 8B only
  • Ephemeral reasoning loses the thread near the end of the task, however often the model thinks 8B only

Open

  • Why the kept reasoning prevents the eating: not tested (read the reasonings before an eat).
  • e1, er4, r4, grand50 of the 8B have 50 games; lr4 has 150.
  • The win rate was not a planned measure.
  • gpt-oss in the format it was trained on with its reasoning in view (the game as tool calls).
  • Labels of the reasonings are a model's, no human check yet.
